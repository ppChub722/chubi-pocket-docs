# API audit: calls per page and client-side joins (2026-10-12)

Read-only audit by Lead's Explore agent, on the owner's request ("check the API design: how many APIs does one page call?").
Paths are relative to the workspace root: `app/` means `chubi-pocket-app/lib/`, `be/` means `chubi-pocket-be/internal/modules/`. Endpoints are under `/api/v1`.

## 0. Global
- **One Dio** (`app/core/network/api_client.dart`); repositories call it directly.
- **App-wide cubits** (`app/app/app.dart:198-242`):
  - loaded once: Accounts, Categories (active only), Tags
  - Contacts: `loadIfNeeded`, but the contacts and debts pages call `load()` every visit
  - Projects: `load()` every time
  - PersonalDebts: `listAll` on every debts visit
- **Home warms the caches:** it loads accounts + categories (`home_page.dart:85-86`) so that `TransactionTile` can draw icons. Deep links render worse.
- **Boot:** GET /app/version (also on resume), GET /users/me.
- **Badge:** polls `GET /notifications?read=false&per_page=1` every 30s. There's no count endpoint, and it double-starts at login (`app.dart:213, 267-268, 361`).

## 1. Calls on open, per page
| Page | Calls (warm/cold) | Reference lists loaded only for lookups | Notes |
|---|---|---|---|
| Home | ~6–8 cold | /accounts, /categories | ping-pong between the badge and the inbox: a hidden GET /notifications per badge change |
| Transactions list | 2 | /tags (only the filter sheet needs it) | every row joins the categories + accounts caches |
| **Transaction detail** | 0–3 | /contacts (whole list) when there are splits | cold: GET /transactions page 1 just to find the row, then /:id; split rows always cost a GET /:id; a transfer twin = the whole day's transfers (no lookup by group); `isSystem` / repayment need the categories cache |
| Wallet detail | 0–1 / 2–3 | — | a wallet that's not active → the whole archived list (GET /accounts/:id unused); the members tab re-fetches members that are already embedded |
| **Debts list** | 1+⌈N/100⌉ every visit | /contacts (avatar icons) | downloads ALL debts (all statuses) and aggregates client-side; `/personal-debts/people` (live name, icon, totals) exists but is never called |
| Debt person page | 0 / ⌈N/100⌉ | — | cold = every debt to filter one person (the BE `counterparty_contact_id` filter is unused); the title depends on the entry point |
| Debt detail | 0 / 1 | contacts cache (icon) | name = the snapshot |
| Contact detail | 2 | — | GET /contacts/:id always + GET /contacts/unlinked-names (global) |
| **Pending** | 1–2 / 4 | /accounts, /categories, /tags | drafts carry bare ids; each row joins 3 caches |
| Quick create | 1 first / 4 cold | accounts, categories, tags (pickers) + /contacts on first open even with no split | after each save a full GET /accounts, though POST returns `account_balance_after` (`patchBalance` is never used) |
| Event picker | 1 every open | — | GET /projects each time |
| More hub | 0 / 3 | /categories, /tags (counts only) | |
| Category detail | 1–2 | — | GET /users/me every open (fee flag) |
| Scheduled detail | 1 | — | never loads the entry → "not found" in a fresh session (bug) |
| Notifications inbox | 1 + badge | — | `unread_count` is already in the list response, yet the badge still refreshes |

No per-row N+1 on open. The near equivalents:
- the `listAll` paging on debts
- `bookChanged` re-fetches every live list after each write
- `setTags` = one DELETE per removed tag + POST + GET
- bulk pending discard = one DELETE per draft
- one quick-create save ≈ 5+ calls

## 2. Worst offenders
1. Debts list / person page: everything downloaded every visit and aggregated client-side; `/people` unused.
2. Transaction detail: a list page fetched to find the row, an extra GET /:id for splits, the whole day's transfers for the twin, the whole contacts list for avatars, the categories cache for the system flag.
3. Home: accounts + categories loaded only for tile icons, plus the notification ping-pong.
4. Pending: 3 reference lists to render bare-id drafts.
5. `TransactionTile` everywhere depends on the category/account caches (icon, localized system name, wallet icon). Those caches are active-only, so archived items miss.
6. The wallet/accounts pages fetch the whole archived list; More loads 2 full lists for counts; category detail calls /users/me every open.

## 3. BE: embedded display data vs bare ids
**Embedded today:**
- `TransactionDetail`: `account` / `category` as `EmbeddedRef{id,name}` only, with no icon, parent icon or system kind (`be/transactions/model.go:92-95`, `store.go:245-249`)
- tags with icon; `project{id,name}`; `category_render` only on shared-wallet rows
- dashboard `recent`: the same gaps
- budgets: category with icon
- goals: `linked_account` without icon
- accounts: `members[]` with icon
- contacts: linked user name/icon live; project members: name/icon

**Bare ids the FE looks up:**
- `EmbeddedRef` without icon/system kind → the categories + accounts caches on every tx row
- `SplitRef`: `person_name` + `contact_id` only → the contacts cache for icon / linked state
- `PersonalDebt`: `counterparty_contact_id` + the snapshot name only
- pending `draft`: account/category/transfer/tag/project/split-contact ids, all bare (`be/pending/model.go:30-42`)
- notification settings: `default_account_id`
- project transactions: member ids
- no transfer-twin reference (direction is guessed from the category name containing "out", `app/features/transactions/domain/transaction.dart:244-251`)

**Snapshot vs live name (spec 07-contacts.md:45, 06-shared-expenses.md:110):**
- the spec says that when `contact_id` is set, the display comes from the LIVE contact name
- the BE returns the stored snapshot with no contacts join: `SplitsFor` (`be/transactions/store.go:794-803`), debt `GetByID` / `List` (`be/personal_debts/store.go:64-68, 280-281, 340-345`)
- the FE renders the snapshot everywhere, so renamed contacts show their old names
- the only live join is `/personal-debts/people` (`store.go:518-553`): unused, and it uses `contacts.display_name`, not the linked user's name

## 4. Side bugs found
- `app/features/personal_debts/data/personal_debts_repository.dart:99`: `'/personal-debts/split-changes//apply'`, so the notification id is never interpolated. This is the "อัปเดตตาม" bug.
- Scheduled detail never loads its entry (`scheduled_transaction_detail_page.dart:41-69`). Opened from the Home "coming up" card in a fresh session, it shows "not found".
- The drill-down category filter is silently dropped when categories aren't cached (`transactions_list_page.dart:107-117`).
- The debt person page title depends on the entry point (snapshot vs contact name).
