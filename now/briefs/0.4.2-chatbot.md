_Lead, 2026-10-30. Split out of `now/briefs/0.4.2-plan.md` (owner 2026-10-30: "ทำ plan แยกจาก 0.4.2-plan เป็น 0.4.2-chatbot"). Builds on 0.4.2-2 (Telegram linking + login, migrations 121–123). This file is the truth for the chatbot; 0.4.2-plan keeps the history and the later phases._

## Owner decisions (2026-10-30)
- **Simple first ("เอาแบบใช้ง่ายๆ"):** Telegram chat only. Every text message = one fresh input turned into JSON. No chat memory.
- **Buttons:** [✓ ยืนยัน] = book it into the app now; [✗ ยกเลิก] = throw it away.
- **Not enough data:** one short error line saying why; nothing is created, nothing waits. The next message is a new JSON.
- **Edit only by Telegram Reply** on the bot's card ("ต้องมี reply เท่านั้น"). No reply = a new input, always.
- **Many pending rows are fine.**
- **Provider:** Anthropic API (not the Claude CLI, not a cheaper provider). **Model: Haiku 5.5 only** ("Opus 5.5 ไม่ต้อง"); no Opus comparison.

## Flow
```
text (no reply)  → LLM → items[] → pending rows (source telegram) → card + [✓ ยืนยัน] [✗ ยกเลิก]
text (reply to a card) → LLM(card items + edit text) → items[] → replace that card's rows → edit the card
✓ → submit the card's rows (same call as the app) → card "บันทึกแล้ว ✓"
✗ → discard the card's rows                    → card "ยกเลิกแล้ว"
no bookable item → one error line, nothing saved (a reply edit: the old rows stay)
```
- One message with several items = one card, one pair of buttons (all or nothing).
- Linked chat + `chat` permission on = allowed (the 0.4.2-2 rules: unlinked → "เชื่อมบัญชีก่อนนะครับ…", permission off → "ปิดการจดรายการไว้ เปิดได้ในแอป").
- Not text (photo, voice, sticker) → "ตอนนี้รับแค่ข้อความตัวอักษรนะครับ" (as in 1a).

## JSON contract
**Context sent to the LLM** (system prompt fixed and cached; this part after it): today (Asia/Bangkok, with weekday), wallets `[{id:"w1", name, main}]`, categories `[{id:"c1", name, type, parent}]` as short aliases. The BE maps aliases back to UUIDs; an alias outside the list becomes null. Archived wallets / categories are left out.

**Output (structured output schema)**
```json
{
  "items": [{
    "type": "expense | income | transfer",
    "amount": 60,
    "description": "ข้าว",
    "category": "c3",
    "account": null,
    "transfer_to": null,
    "date": "2026-10-30",
    "note": null,
    "unsure": ["category"]
  }],
  "reply_hint": "no_amount | not_money | transfer_wallet_missing | null"
}
```
- **No free text from the model (owner 2026-10-30: "ทุกอย่างต้องเป็น enum หรือ structure data เท่านั้น").** Every field is an enum, an alias from the given lists, a number, an ISO date, or a VERBATIM copy of the user's words: `description` and `note` must be exact substrings of the input (for a Reply edit: of the edit text or the card's current values). The BE checks each with a plain substring test (after trimming / collapsing spaces) and sets a field that fails to null; the model never rewrites, translates or summarises. Date: a regex-checked `YYYY-MM-DD`; amount: a number > 0.
- `description` = the user's words for what it is (≤ 50, no amount / date in it); `note` = the user's remaining words (≤ 200). `date` ISO, null = today. `account` null = main wallet. `category` null when not sure (a tx may have no category). `unsure` = fields the model guessed; shown as "?" on the card.
- `amount` null / ≤ 0 or `type` unknown → the BE drops that item. `transfer` needs `account` and `transfer_to` (different), else dropped. No item left → the bot replies the fixed text of `reply_hint`.
- **`reply_hint` is an enum, never free text (owner 2026-10-30: "ต้องเป็น enum รองรับแค่ไม่กี่อย่าง นอกเหนือจากนี้ไม่ได้").** Only when `items` is empty; the BE maps each value to its fixed Thai line; null or an unknown value with no item → `not_money`:
  | Value | Bot says |
  |---|---|
  | `no_amount` | ไม่เห็นยอดเงินครับ ลองพิมพ์ใหม่ เช่น ข้าว 60 |
  | `not_money` | จดได้แค่รายรับ รายจ่าย และการโอนครับ |
  | `transfer_wallet_missing` | บอกกระเป๋าต้นทางและปลายทางด้วยครับ |
  New values only by a contract change (owner's OK).
- The model never invents ids and never asks a question. The bot never sends a word the model wrote: the card shows fixed BE text, names from the user's own lists, and the user's own words copied by the model.

**Off-topic and prompt-injection guard (owner 2026-10-30)**
- Structured output only: nothing outside the schema can reach the user; off-topic / "ignore your instructions" messages → `items: []` + `not_money`.
- The system prompt states the user's text is data to convert, never instructions.
- Input ≤ 500 characters (as parse-text), checked by the BE before the call ("ข้อความยาวเกินไปครับ"); a small `max_tokens` on the output.
- Ids only from the user's own enums, validated by the BE; nothing books without ✓; the monthly + per-minute caps bound the cost of abuse.
- Each item maps 1:1 to the existing pending `Draft` (`type, amount, account_id, category_id, date, description, note, transfer_to_account_id`), so validation and the resolver are reused.

**Card (BE-built):**
```
🧾 2 รายการ
รายจ่าย 60 ฿ · ข้าว · อาหาร · วันนี้
รายจ่าย 45 ฿ · กาแฟ · ? · วันนี้
[✓ ยืนยัน] [✗ ยกเลิก]
```
After a tap the card is edited to "บันทึกแล้ว ✓" / "ยกเลิกแล้ว" (buttons removed).

## Edit by reply
- A message WITH `reply_to_message` = edit the rows of that card; WITHOUT = a new input. Never guessed, no "current" pending. The link is the card's `chat_id + message_id`, stored in each row's `source_ref`.
- The LLM gets the card's current items (same JSON shape) + the edit text and returns the FULL replacement `items[]` (same schema, same rules). The BE replaces the card's rows and edits the card in place. Not enough data → the error line, the old rows stay.
- Reply to a card that is finished (✓ / ✗, or handled in the app), or to any other message → "รายการนี้จัดการไปแล้วครับ" (a non-card message: "ตอบกลับได้เฉพาะการ์ดรายการครับ"). A stale button tap answers the same.
- Example edits: "เปลี่ยนเป็น 70" · "หมวดกาแฟ" · "เมื่อวาน" · "ใช้กระเป๋ากสิกร" · "ลบกาแฟออก" (multi-item card).

## Many pending rows
- Each card is independent. Telegram rows also show in the app's pending page (source Telegram) and can be confirmed / discarded there; a card handled in the app turns stale in Telegram (above). No auto-expiry in v1.
