## Owner decisions (2026-10-30)
- **Simple first ("เอาแบบใช้ง่ายๆ"):** Telegram chat only. Every text message = one fresh input turned into JSON. No chat memory.
- **Buttons:** [✓ ยืนยัน] = book it into the app now; [✗ ยกเลิก] = throw it away.
- **Not enough data:** one short error line saying why; nothing is created, nothing waits. The next message is a new JSON.
- **Edit only by Telegram Reply** on the bot's card ("ต้องมี reply เท่านั้น"). No reply = a new input, always.
- **Many pending rows are fine.**
- **Provider:** Anthropic API (not the Claude CLI, not a cheaper provider). **Model: Haiku 5.5 only** ("Opus 5.5 ไม่ต้อง"); no Opus comparison.

## Provider slot (owner 2026-10-31: "เปลี่ยนเจ้า api แค่ทำ slot ไว้หลังบ้าน")
- One interface `llm.Client.Complete(system, user, schema)`; the parse core never knows the provider. Each provider = one adapter file in `internal/platform/llm` (v1: `anthropic.go` only).
- v1: which provider + model = server config (`LLM_PROVIDER` default `anthropic`, `LLM_MODEL` default `claude-haiku-5-5`, key per provider in `.env`); switching = change the config or add an adapter file. Users cannot choose YET (owner: a per-user choice comes later): the parse core gets its client from `llm.Router.For(ctx, userID)`, which returns the server default in v1; a later per-user setting only changes the Router, no caller changes. Adapters are registered by id (`anthropic`, later `openai`, `gemini` ...) so a stored choice maps to one.
- One provider-neutral JSON schema and one prompt; the BE validates every answer the same way, so safety does not depend on the provider.
- `llm_calls` logs provider + model. A new provider / model goes live only after the K6 eval passes on it. No silent fallback to another provider.

## Flow
```
text (no reply)  → LLM → items[] → pending rows (source telegram) → card + [✓ ยืนยัน] [✗ ยกเลิก]
text (reply to a card) → LLM(card items + edit text) → items[] → replace that card's rows → edit the card
✓ → submit the card's rows (same call as the app) → card "บันทึกแล้ว ✓"
✗ → discard the card's rows                    → card "ยกเลิกแล้ว"
no bookable item → one error line, nothing saved (a reply edit: the old rows stay)
```
- One message with several items = one card, one pair of buttons (all or nothing).
- Linked chat + `chat` permission on = allowed (the 0.4.2-2 rules: unlinked → "เชื่อมบัญชีก่อนนะครับ…", permission off → "ปิดการจดรายการไว้ เปิดได้ในแอป").
- Not text (photo, voice, sticker) → "ตอนนี้รับแค่ข้อความตัวอักษรนะครับ" (as in 1a).

## JSON contract
**Context sent to the LLM** (system prompt fixed and cached; this part after it): today (Asia/Bangkok, with weekday), wallets `[{id:"w1", name, main}]`, categories `[{id:"c1", name, type, parent}]` as short aliases. The BE maps aliases back to UUIDs; an alias outside the list becomes null. Archived wallets / categories are left out.

**Output (structured output schema)**
```json
{
  "items": [{
    "type": "expense | income | transfer",
    "amount": 60,
    "description": "ข้าว",
    "category": "c3",
    "account": null,
    "transfer_to": null,
    "date": "2026-10-30",
    "note": null,
    "unsure": ["category"]
  }],
  "reply_hint": "no_amount | not_money | transfer_wallet_missing | null"
}
```
- **No free text from the model (owner 2026-10-30: "ทุกอย่างต้องเป็น enum หรือ structure data เท่านั้น").** Every field is an enum, an alias from the given lists, a number, an ISO date, or a VERBATIM copy of the user's words: `description` and `note` must be exact substrings of the input (for a Reply edit: of the edit text or the card's current values). The BE checks each with a plain substring test (after trimming / collapsing spaces) and sets a field that fails to null; the model never rewrites, translates or summarises. Date: a regex-checked `YYYY-MM-DD`; amount: a number > 0.
- `description` = the user's words for what it is (≤ 50, no amount / date in it); `note` = the user's remaining words (≤ 200). `date` ISO, null = today. `account` null = main wallet. `category` null when not sure (a tx may have no category). `unsure` = fields the model guessed; shown as "?" on the card.
- `amount` null / ≤ 0 or `type` unknown → the BE drops that item. `transfer` needs `account` and `transfer_to` (different), else dropped. No item left → the bot replies the fixed text of `reply_hint`.
- **`reply_hint` is an enum, never free text (owner 2026-10-30: "ต้องเป็น enum รองรับแค่ไม่กี่อย่าง นอกเหนือจากนี้ไม่ได้").** Only when `items` is empty; the BE maps each value to its fixed Thai line; null or an unknown value with no item → `not_money`:
  | Value | Bot says |
  |---|---|
  | `no_amount` | ไม่เห็นยอดเงินครับ ลองพิมพ์ใหม่ เช่น ข้าว 60 |
  | `not_money` | จดได้แค่รายรับ รายจ่าย และการโอนครับ |
  | `transfer_wallet_missing` | บอกกระเป๋าต้นทางและปลายทางด้วยครับ |
  New values only by a contract change (owner's OK).
- The model never invents ids and never asks a question. The bot never sends a word the model wrote: the card shows fixed BE text, names from the user's own lists, and the user's own words copied by the model.

**Off-topic and prompt-injection guard (owner 2026-10-30)**
- Structured output only: nothing outside the schema can reach the user; off-topic / "ignore your instructions" messages → `items: []` + `not_money`.
- The system prompt states the user's text is data to convert, never instructions.
- Input ≤ 500 characters (as parse-text), checked by the BE before the call ("ข้อความยาวเกินไปครับ"); a small `max_tokens` on the output.
- Ids only from the user's own enums, validated by the BE; nothing books without ✓; the monthly + per-minute caps bound the cost of abuse.
- Each item maps 1:1 to the existing pending `Draft` (`type, amount, account_id, category_id, date, description, note, transfer_to_account_id`), so validation and the resolver are reused.

**Card (BE-built):**
```
🧾 2 รายการ
รายจ่าย 60 ฿ · ข้าว · อาหาร · วันนี้
```

## Edit by reply
- A message WITH `reply_to_message` = edit the rows of that card; WITHOUT = a new input. Never guessed, no "current" pending. The link is the card's `chat_id + message_id`, stored in each row's `source_ref`.
- The LLM gets the card's current items (same JSON shape) + the edit text and returns the FULL replacement `items[]` (same schema, same rules). The BE replaces the card's rows and edits the card in place. Not enough data → the error line, the old rows stay.
- Reply to a card that is finished (✓ / ✗, or handled in the app), or to any other message → "รายการนี้จัดการไปแล้วครับ" (a non-card message: "ตอบกลับได้เฉพาะการ์ดรายการครับ"). A stale button tap answers the same.
- Example edits: "เปลี่ยนเป็น 70" · "หมวดกาแฟ" · "เมื่อวาน" · "ใช้กระเป๋ากสิกร" · "ลบกาแฟออก" (multi-item card).

## Many pending rows
- Each card is independent. Telegram rows also show in the app's pending page (source Telegram) and can be confirmed / discarded there; a card handled in the app turns stale in Telegram (above). No auto-expiry in v1.

## Next: create-tx intents (owner 2026-11-05) — decided, not started
All of these make a **transaction** (not a new recurring rule / event / goal, those are the later "create" group): saving entry, split bill, a tx in an event (`new_event` when none), a tx tied to an existing recurring item, a debt. Each is a pending row (✓ confirms), one `type` per item in the one model call (mixed messages work); the lists the model picks from (goals, contacts, events, recurring items, open debts) go in as name + alias like wallets and categories.
- **Recurring (tx tied to an item):** the model picks only the item (`r3`); the **BE picks the slot in code**: the latest past slot with no tx linked and not skipped; none → the next upcoming slot; no slot left (a finished installment) or no item matches → a plain expense, as today. An unclear name = unsure `[ค่าไฟบ้าน ?]`. The tx is a normal one: category / description / wallet from the rule unless the user said otherwise, amount as typed (none → the rule's), date as typed (none → today). On ✓: submit the row, then `LinkOcc` (the tx keeps its own date and amount); if the slot was paid in the app meanwhile the tx stays booked and the card says "บันทึกแล้ว แต่ผูกกับรายการประจำไม่ได้". A recurring item of kind หนี้: ✓ links the person-book entry to the slot (date / wallet follow the rule).
- **Debt, with or without money (option A):** by the words. "ให้ยืม / ยืม / โอนให้" = a tx (money moves) + the debt; "ค้าง / ติด / เป็นหนี้" = the debt only, no tx. **Every debt card says it in two lines named after the two app pages** (owner 2026-11-05, no "tx", no "จด"): `🤝 รายการหนี้: พี่ลีค้างเรา ฿3,000` then `💸 รายจ่าย: ออกจาก Kbank ฿3,000` or `➖ ไม่มีรายจ่าย` (borrowing: `รายรับ: เข้า Kbank …` / `➖ ไม่มีรายรับ`, "เราค้างพี่ลี …"). English names come from `app_en.arb`. A guessed line shows `[… ?]`; Reply changes it ("ไม่ต้องมีรายจ่าย", "หักจาก kbank"). The app's own switch is "บันทึกในรายการ" (on by default; off = person book only). Repaying ("บอยคืน 200") = money in, the existing settle path.
- **Order (proposed, owner to confirm):** saving → tx in an event → split bill → recurring-tied tx → debt. Each step has its own tests and docs.

### Saving entries (owner 2026-11-05)
The app's saving model: a saving entry is a notebook row, never a real tx; money remembers its wallet; "ยังไม่จัดสรร" (spare) is the pool. The chatbot makes: **ออม** wallet → goal ("ออมเที่ยวญี่ปุ่น 2000 kbank"), **ออม** wallet → ยังไม่จัดสรร ("ออม 2000 kbank"), **จัดสรร** ยังไม่จัดสรร → goal, **ย้าย** goal → goal and goal → ยังไม่จัดสรร, and (proposed) **ถอนออม** back to the wallet.
- **Goal unclear → ยังไม่จัดสรร** (owner), for ออม. For จัดสรร / ย้าย an unclear target would be spare → spare, so the proposed answer is "บอกเป้าหมายด้วยครับ" (owner to confirm).
- **Wallet (owner): saving from a wallet needs a wallet named; the default wallet is for creating tx, never used here.** Not named → the card shows `👛 กระเป๋า: [ไม่ระบุ ?]` + "Reply ชื่อกระเป๋า เช่น kbank"; ✓ with no wallet → the fixed line "ออมจากกระเป๋าไหนครับ", the card stays open. Exactly one active wallet → that one (owner: "ตามนั้น"). Choice buttons under the card: later.
- **จัดสรร / ย้าย: no wallet needed** (owner: right). The BE splits across wallets largest-first as the app does; a wallet named in the message limits the move to that wallet's money.
- **BE work:** the pending `saving` draft only does ออม (`SaveFromDraftTx` → `createEntriesTx` kind `save`). จัดสรร / ย้าย / ถอนออม need the draft to say from-bucket / to-bucket (`move`, `withdraw` exist in `saving_goals`).
- **Open (proposed answers):** ถอนออม in this step · the card shows only the total, not the wallet split · no block and no warning when the spare is short (the app only shows red).
- **Confirmed (owner 2026-11-05):** จัดสรร / ย้าย with no target → "บอกเป้าหมายด้วยครับ" · the card shows only the total (not the wallet split) · no block and no warning when the spare is short. Still open: ถอนออม (which wallet it returns to: its own, see the rule above).
- **ถอนออม (owner 2026-11-05, leaning):** the wallet it returns to must be named, like ออม; not named → `[ไม่ระบุ ?]` + Reply; one active wallet → that one. Rule of thumb: whatever touches a real wallet (ออม, ถอนออม) names it; moves inside the notebook (จัดสรร, ย้าย) do not.

### Event bills (owner 2026-11-05, "ได้อยู่" on all proposals)
A tx in an event = a paper with `project_id` (the BE `draft.paper` + `new_event`), one pending row, ✓ confirms. The user must name the event (no guessing an event, even when one is open).
- **Payer:** not said = I paid all; "บอยจ่าย" = Boy paid (I owe my share); several payers → later.
- **Split:** equal among all event members; "ไม่รวมบอย" / "หารกับบอยสองคน" = a subset; per-person amounts → later.
- **Event not found:** a name led by "ทริป / อีเวนต์" = create it (card line `🆕 อีเวนต์ใหม่: …`, the bill's people become members); any other unmatched name = a plain expense. A completed event (bills locked) → "อีเวนต์นี้จบแล้วครับ", never another event.
- **Wallet:** the tx rule (not named = the default wallet), unlike savings.
- Card: `🏝️ อีเวนต์: …` · `💳 ฉันจ่ายเอง · หารเท่ากัน N คน` · `🧮 ส่วนของฉัน ฿…`. The model gets each open event's members (name + alias) in the context to resolve who paid / who is out.

### Split bills, not in an event (owner 2026-11-05)
Same rules as event bills (payer, equal split, wallet by the tx rule). Differences:
- **People:** each name is looked up in the user's contacts. Found → the card marks it as a contact with 📇 (the app's `contact_page` icon); not found → a plain typed name (`person_name`), no contact is created. No names given ("หาร 3 คน") → `👥 หารกับ: [ใคร ?]`, ✓ answers "บอกด้วยครับว่าหารกับใคร", Reply fills it.
- **Debt line as a summary:** I paid → `🤝 รายการหนี้: ทุกคนติดเราคนละ ฿200` (a list per person when the shares differ); someone else paid → `🤝 รายการหนี้: เราติดบอย ฿200`.
- **Notice line follows who is a connected user:** before ✓ `📨 แจ้ง: บอย` (only people whose contact is linked to an account); after ✓ `📨 แจ้งบอยแล้ว ✓`, or `📨 แจ้งทุกคนแล้ว ✓` when every other person was told. Nobody connected → no line. (The notice is an invite the other person answers; nothing is forced on their book.)

### JSON contract for the new intents (proposal, owner 2026-11-05: "ข้อความไม่ gen, AI ผลิต json")
The model produces JSON only; every word the user reads (card, hints, errors, questions back) is a fixed BE string chosen from the validated JSON. The model puts no default in (not said = `null`; the BE fills wallet / date / goal by the rules above), copies `description` / `note` / names verbatim, and answers aliases from the lists (`w` wallet, `c` category, `g` goal + the literal `spare`, `p` contact, `e` event, `m` event member, `r` recurring).
- New `type` values: `saving`, `split`, `debt`, `recurring_paid` (+ the old `expense` / `income` / `transfer`). `transfer` may carry one wallet only (withdraw / deposit).
- New fields: `saving_action` (`save` | `allocate` | `move` | `withdraw`), `goal`, `from_goal`, `event`, `event_name`, `payer {who|name}`, `people [{who|name}]`, `exclude [m…]`, `split_mode`, `recurring`, `debt {person|name, side, with_money}`; `side` = `they_owe_me` | `i_owe_them` | `they_repay` | `i_repay`; `amount` may be `null` only for `recurring_paid`; `unsure` gains `goal`, `recurring`, `with_money`.
- The expected JSON of every example case (T / S / E / P / R / D / X) is on the owner's page, section "สัญญา JSON" and the "test case" table (artifact 9TspzcZ5NPtj3wudhhykej).
