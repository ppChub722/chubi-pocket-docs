## F. Notification model + event members (owner 2026-10-30; decided, not started — "ปล่อย 0.4.2-3")

**F1. แจ้ง and อัตโนมัติ are independent** (supersedes "auto off locks แจ้ง on" in section A, commit `e2b7da7`, and `notifyLocked` in the app).
| แจ้ง | auto | result |
|---|---|---|
| on | on | notice in the inbox, already applied ("as if I did it") |
| on | off | notice in the inbox, waits for my answer |
| off | on | no notice; applied silently |
| off | off | no notice; nothing happens (the bill never enters my book; the sender's book may still say I owe) |
- BE: `Delivery.Insert` (`notifications/dispatcher.go`) stops forcing "ask" notices when muted (`askTypes` rule goes: shared_bill_created / project_tx_changed / shared_bill_deleted).
- App: the แจ้ง switch is never locked; drop `notifLockedByAutoHint`. The delete row keeps a blank auto cell (mirror).
- Already done in the app tree (uncommitted, 2026-10-30): legend moved under the groups, "–" cells now blank, delete row's auto cell blank.

**F2. Event invites.** A linked person added to an event (quick create, bill people, split → quick event) becomes a normal member right away, NOT linked yet (`user_id` NULL, status active) and gets ONE `project_invite`; no other notice before that. Everyone in the event can bill / pay / split with them as a normal member. Accept (or auto-accept) → `user_id` set (`LinkMemberToUserTx`, unchanged). Reject → nothing: the member stays a plain name, the invitee gets nothing else, nothing is linked. No duplicate invite for a member already in the event (also after a reject).
- Single choke point: `quickMemberBuilder.ensureLinked` (`projects/quick.go`): today it inserts an ACTIVE LINKED member + `project_added`.
- Retire `project_added` (stop dispatching, drop it from the settings list and the app row "ถูกเพิ่มเข้าอีเวนต์"; old notices stay readable).
- Settings (owner 2026-10-30, DECIDED): the "คำเชิญและคำขอ" group splits into THREE rows — เชิญเข้าอีเวนต์, ขอเชื่อมผู้ติดต่อ, ชวนใช้กระเป๋า — each with [แจ้ง] [อัตโนมัติ], all mutable, all auto-acceptable, same four-case table as F1. Each auto is its OWN new `users` flag (default off): `auto_accept_event_invites`, `auto_accept_contact_links`, `auto_accept_wallet_invites` (the old `auto_accept_events` stays "accept the event bills into my book"). Needs: migration for the three flags, `PUT /users/me` fields, `actionTypes` (never muted / never auto) shrinks to nothing, BE auto-apply on create for each of the three, app rows + switches, the contact / wallet pages show the same switch where the event / person pages already do.

**F3. Member ↔ contact: per viewer.** New table `project_member_contacts(project_member_id, user_id, contact_id)` — "which of MY contacts is this member"; unique (`project_member_id`, `user_id`); `contact_id` → `contacts` `ON DELETE CASCADE` (deleting a contact makes the member a plain name again). `project_members.contact_id` stays dropped (migration 000027: a contact is per user). No backfill of old members.
- Resolve for a viewer: own member = "me" → `user_id` set and the viewer has a contact with that `linked_user_id` → that contact (linked) → a row in `project_member_contacts` for the viewer → that contact → else a plain name with "add to my contacts". Old members with no row keep today's by-name fallback so existing events don't change.
- Adding a person from a contact writes a row for the adder. Dedup of the same contact = through the adder's own rows / `user_id`, never by name for new members.
- NO auto-merge by name: two people's "แม่" are different people. A viewer binds a member to his contact himself (new API: bind / unbind my contact on a member; app: "ผูกกับผู้ติดต่อของฉัน" + "เพิ่มเข้าผู้ติดต่อของฉัน" on the members page). Personal-book rows typed as a name stay as they are; the contact page's existing "ผูกชื่อที่เคยพิมพ์ไว้" is how he merges them.
- Worked scenario (me + mom + brother + girlfriend; girlfriend not accepted yet) with the table states is in the 2026-10-30 chat; the rule above reproduces it.
