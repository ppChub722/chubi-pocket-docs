## Process
- **Testing (owner 2026-10-13):** devs do NOT run the full analyze / test suite; they run ONLY the tests for what they changed (those test files; BE only the changed packages; no whole folders, no test/ui + test/hub sweeps). LEAD runs the full flutter analyze + flutter test and go vet + go test ONCE when everyone is done, then routes failures to file owners. DONE pings are one line.
- The owner talks only to Lead. Lead discusses and sends briefs only on an explicit order ("จัด" / "ทำเลย" / "แก้เลย"). Bugs too: propose, then wait.
- The owner controls pacing: commits, deploys and builds happen only on a go. A go relayed by Lead counts for DevOps.
- Team language is English. Lead ↔ owner is Thai. No AI attribution in commits or PRs.
- Minimal cross-session messages: message a session only when it must act. Reports go to `team/inbox/`, questions go to Lead.
- Devs may talk to each other directly (owner 2026-10-11): shared files, kit/API needs, blockers, handoffs. DONE pings and owner-level questions still go to Lead.
- Only the owner runs the app (`./run-web.sh`), except QA, which may run it locally (never prod).
- QA runs only on the owner's order; checklists list the changed items only; no screenshots by default; FAILs + a PASS count.
- Local builds happen ONLY when the owner orders one (owner 2026-10-13, final). Lead just reports "done"; the owner builds and checks, and anything wrong gets fixed. No QA verification unless the owner orders it (QA is token-heavy).
- QA may create any data it needs in the LOCAL DB without asking (owner 2026-10-11). Never prod.
- QA runs NO servers: DevOps brings up the local BE + web (:5181). QA scripts persist in `team/qa/` and get reused (explore only new pages); screenshots go to `team/qa/shots/<date>/` (gitignored). (owner 2026-10-11)
- **Tag-based releases (owner 2026-10-13):**
  - "สั่ง release" = Lead commits (several commits OK), bumps the version, tags `v<version>` in be / app / docs and pushes
  - DevOps deploys FROM THE TAG in a separate worktree: checks there, then BE + migrations, APK, env, verify; one final report. DevOps never commits / tags / pushes
  - any tag can be redeployed or rolled back; the team keeps working during a release
- Versioning `0.3.1-N`; build = app commit count. **From 0.3.1-9 every release forces the update (`MIN_APP_BUILD` = the new build, owner 2026-10-12)**, so old app builds never constrain the API: breaking changes are fine.
- Data is disposable (DB wipe OK); migration squash is planned.
- **Shared AI notes (owner 2026-10-20):** several AI sessions work at once, so notes, decisions, status and reports go into `chubi-pocket-docs` (`now/STATUS.md`, `rules/decisions.md`, `now/backlog.md`, `team/inbox/`). A session's private memory is not enough.
- **Edits (owner 2026-10-19):** change code with the Read + Edit tools, not python / sed scripts. A script is OK only for a 100+-site mechanical sweep, and it must be announced first.
- **Page-by-page rounds (owner 2026-10-21, from 0.4.0-3):** the owner talks through ONE page at a time with Lead until it is settled; Lead briefs fe-A (or others) per page right away and keeps going. No more one big batch at the end. 0.4.0-3 scope = UI + logic polish of the debts and events pages, plus bugs the owner reports from 0.4.0-2.
- **Debt model (owner 2026-10-21, 0.4.0-3, not built yet):** a DEBT is a ledger record (personal_debts), e.g. a split meal or a loan; it may carry its own linked tx (the 500 borrowed lands in a wallet), and that tx does NOT reduce the balance. A REPAYMENT is a TRANSACTION tied to the PERSON ("จ่ายหนี้ให้ลี 400"), not a debt row. Balance per person = Σ debts − Σ repayment txs (60 + 500 + 70 − 400 = 230). "จ่ายแล้ว" is an optional label the user sets per debt (never set automatically); when set it SHOWS on that debt (its row in the person statement + a chip in the debt's hero); the balance alone decides when it's done (0 = cleared). The code today stores repayments as opposite-direction debt rows → BE + quick create change needed.
- **Paid by someone else (owner 2026-10-21, 0.4.0-3, concept agreed, UI placement open):** when someone pays for me, I still record a REAL expense tx (category, my share) with NO wallet: no money leaves my wallets then. The same save creates the debt I owe. Money leaves a wallet only later, with the repayment tx. Same for a partner's split once accepted. UI (agreed): quick create tx mode, section ผูกกับ gets a row "คนจ่ายแทน" under "แบ่งกับคน"; the two are exclusive (the complex mixed case = the payer does the split). SUPERSEDED (variant B, same day): the top amount = the BILL in แบ่ง / จ่ายแทน / อีเวนต์ ("จำนวนเงิน" in ส่วนตัว); the line under it shows my share. Old text: the top amount = MY share (my expense); คนจ่ายแทน carries how much they paid (default = all → no wallet; partial → the rest from the chosen wallet); a 3-line result box (expense / wallet / debt). REVISED same day: แบ่งกับคน / คนจ่ายแทน / อีเวนต์ are mutually exclusive (รายการประจำ combines with any). Picking an event opens its own bill UI under the event row: ใครจ่าย (one, free choice) + ใครอยู่ในบิล (free multi-choice) + how to divide. Picking someone who isn't an event member, or typing a new name, AUTO-ADDS them as a member (no prompt). Switching to the event carries over what was typed: แบ่งกับคน → payer = me, members = me + those people; คนจ่ายแทน → payer = that person, members = me + them; removing the event moves it back. They are three views of ONE shared data set (people in the bill + shares, who paid, how much), so typed data stays when switching.
- **My book vs the event book (owner 2026-10-21):** my transactions are MY book: only I can edit them. An event is a SHARED book: any member can edit its bills fully. A tx of mine linked to an event bill never changes by itself:
  - I edit my linked tx → ask "แก้ในอีเวนต์ด้วยไหม?"
  - I edit the bill in the event → ask "แก้ในสมุดของฉันด้วยไหม?"
  - someone else edits the bill → I get a notification, or later press resolve / update myself; only then does my tx change.
  Saying no, or never resolving, is fine: the two may differ. Every edit on a linked pair ALWAYS asks (or asks whether to notify). To stop the link, delete one side.
  - Exception by the user's own choice: almost every notification type can be set to auto-answer (auto-accept OR auto-reject) in notification settings, including "bill edited → update my tx". Default off except split_created.

## Product
- **My book, my switch (owner 2026-10-27, replaces "Ledger, not sync"):** another user's edit reaches my book automatically only when I turned auto sync on; otherwise a notification asks ("อัปเดตตาม"), and "no" leaves my copy "ไม่ตรง", still connected. - **0.4.1-1 owner answers (2026-10-27; full list in `now/briefs/0.4.1-1-plan.md`):**
  - connect = knows where it came from; sync = same values. Links live only in recurring, debts and events; budgets, wallets and savings read the real txs.
  - Every write that touches a connected side is ONE BE call in ONE DB transaction and answers with `effects` (what changed elsewhere).
  - Only the system writes 0 amounts (sync, auto-create); a typed amount stays > 0; a 0 row can be saved if its amount wasn't touched.
  - Debt ⇄ my own tx: amount, date, description, note are one value. Fields only one side has stay that side's.
  - Recurring: a tx FILLS a slot; deleting the tx skips the slot (last values kept; un-skip = due with them); a skipped slot can be filled directly; skip a filled slot = disconnect first; "จ่ายแล้ว" without a tx needs an amount and counts only in recurring totals (and a "หนี้" kind's person balance); rule edits touch only empty slots.
  - Overdue limit: 3 waiting → the rule pauses ("ค้าง 3 งวด", in ต้องจัดการ); the user turns it on; the next slot = the current period; installments (count end) shift, a date end keeps its date; rules over the limit paused at release.
  - Auto-create never waits and never fails: amount 0 is created; a missing category / wallet → none; no overdue limit; the form warns on amount 0 / a varying amount.
  - Repayments are person-book entries with an optional tx (old no-wallet ones lost their tx); 4 debt system categories (ให้กู้ยืม / กู้ยืม / ชำระหนี้ / รับชำระหนี้), old debt txs moved to them; every system category locks rename + "นับในรายงาน" (icon editable).
  - Debt description is free text; empty = the category name. "ปิดหนี้" on pay back = one switch that labels every open debt with that person paid; just a label, even if the payment is partial.
  - Cross-user debts: each side can disconnect its own copy; the other side is notified; no reconnect.
  - Tx-detail disconnect never changes the bill. Known and kept until 0.4.1-2: switching ผูกกับ off อีเวนต์ / moving event A → B in the tx edit still changes the bill.
- Notify on debt creation (`split_created`) and split edits (`split_changed` / "อัปเดตตาม"). Nothing on pay/receive.
- **Delete vs archive:** ลบ = hard delete; เก็บถาวร = soft (hidden, not counted, restorable). Categories, tags, transactions and debts are delete-only. Plan (done, archived): `archive/engineering/v0.3.3-delete-archive-plan.md`.
